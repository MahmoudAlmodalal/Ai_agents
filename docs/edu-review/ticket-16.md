## 1. مراجعة المخرجات التعليمية

### الموضوع 47 — هندسة أداء قاعدة البيانات (`database-performance-engineering`)

- **المخرج المتوقع:** `docs/DATABASE_PERFORMANCE_REPORT.md`.
- **ما تمت مراجعته:** يطلب الدرس تحديد رحلة ومعيار من SRS وبيئة وحجم بيانات، ثم تسجيل p50/p95 وعدد الاستعلامات والصفوف والأخطاء والزمن قبل التغيير وبعده. يربط معالجة N+1 بتغير عدد الاستعلامات مع عدد الصفوف، والفهرس بخطة استعلام قائمة، والتزامن بظهور اختناق عند حمل ممثل ومؤشرات انتظار أو أخطاء. يطلب تغيير عامل واحد والتحقق من بقاء النتائج الوظيفية صحيحة.
- **دليل القياس أو مبرر عدم الحاجة:** يفرض قالب التقرير توثيق خط الأساس والفرضية والتغيير والمقارنة والمخاطر. يوضح الدرس صراحةً أن عدم ظهور مشكلة عند الحمل المتوقع نتيجة مقبولة، ولا يطلب تحسينًا شكليًا بديلًا عنها. المثال يستخدم `EXPLAIN (ANALYZE, BUFFERS)` لقراءة فقط ويحذر أن `ANALYZE` ينفذ الاستعلام.
- **النتيجة:** **Passed** — المخرج المطلوب قابل للمراجعة ويحتوي معيارًا يمنع ادعاء تحسين بلا دليل. لم يُنفذ benchmark على قاعدة بيانات مشروع طالب ضمن هذه المراجعة.

### الموضوع 48 — Redis (`redis-optional-infrastructure`)

- **المخرج المتوقع:** `docs/REDIS_DECISION.md`، سواء اختار الطالب التجاوز أو تجربة/اعتماد Redis.
- **ما تمت مراجعته:** يعرض الدرس مسارين واضحين: التجاوز عندما تحقق المتطلبات دون مخبأ أو عمل خلفي؛ أو اختبار إضافة مرتبطة بقراءة مكلفة متكررة أثبتها القياس، أو متطلب معتمد لفصل مهمة طويلة. يطلب تحديد مصدر الحقيقة وسياسة TTL والإبطال أو سياسة حالة المهمة وإعادة المحاولة والتكرار، ويشترط مقارنة قبل/بعد.
- **دليل عدم الحاجة أو التبني:** قالب القرار يضم الحالة `Not needed | Trial | Adopted`، والدليل وخط الأساس، ومصدر الحقيقة وسلوك الفشل، وسياسة الصلاحية/الإبطال أو إعادة المحاولة، ونتيجة الفحص وشرط إعادة النظر. يوضح الدرس أن Redis ليس إلزاميًا ولا ينشأ للموقع التعليمي.
- **النتيجة:** **Passed** — مسار التجاوز مكتمل بالمقدار نفسه الذي يراجَع به مسار الاعتماد. لم يُشغّل Redis أو عامل مهام في بيئة اختبار لهذه التذكرة.

### الموضوع 49 — QA (`integrated-project-qa`)

- **المخرج المتوقع:** `docs/FINAL_QA_REPORT.md` وقائمة عيوب قابلة للتكرار أو قرار جاهزية يعلن الفجوات.
- **ما تمت مراجعته:** يربط الدرس كل حالة بمتطلب قبول من PRD/SRS، ثم يفصل فحص التصميم المعتمد والتجاوب عند 390 و768 و1024 و1366 و1440 بكسل والوصول ولوحة المفاتيح والتكامل من الواجهة إلى API وقاعدة البيانات. يتضمن مسار إعادة فحص العيوب بعد إصلاحها.
- **حالات QA والنتائج:** القالب يتضمن حالة ومتطلبًا وبيئة/عرضًا ودليلًا ونتيجة ومتابعة. التعريفات تمنع احتساب غير المنفذ نجاحًا: **Passed** بفحص ودليل، **Failed** بعيب منفذ وموثق، **Not Run** بسبب أو بيئة غير متاحة. ينص الدرس على أن فحصًا آليًا واحدًا لا يثبت امتثال WCAG أو نجاح منتج Full-Stack.
- **النتيجة:** **Passed** — تغطية الفئات المطلوبة ومعيار تسجيل النتائج موجودان بالمادة. لم يُنفذ QA لتطبيق طالب بعينه.

## 2. مراجعة المراجع والروابط

فُحصت المراجع المضافة في المواضيع بوصفها مصادر أولية: وثائق PostgreSQL لـ `EXPLAIN` والفهارس و`pg_stat_statements`، ووثائق Django لتحسين الوصول إلى قاعدة البيانات، ووثائق Redis لـ cache-aside والسلاسل وانتهاء الصلاحية والقياس، ووثائق Celery للمهام، وإرشادات W3C لـ WCAG والتقييم، ووثائق Playwright. رابط Redis cache-aside الحالي هو `https://redis.io/docs/latest/develop/use-cases/cache-aside/`.

**نتيجة التحقق من الروابط:** **Passed** — أعادت الروابط الرسمية الإحدى عشرة حالة HTTP 200 عند الفحص في 2026-10-19. كما تمت مراجعة شرح PostgreSQL لتنبيه تنفيذ `EXPLAIN ANALYZE`، وشرح Redis لنمط cache-aside وTTL، وإرشادات W3C للجمع بين الاختبارات الآلية والمراجعة البشرية. يتضمن اختبار المتصفح فحص الرابط وسمات فتحه الآمن لكل مرجع.

## 3. فحص المتصفح والنسخ والتجاوب

أُنشئ `e2e/path/t16-performance-redis-qa.spec.ts` لزيارة المواضيع الثلاثة وفحص العناوين والمحتوى، ونسخ مثال SQL وقوالب القرار والتقرير والتحقق من النص المنسوخ، ووجود الروابط الرسمية وسمات `target` و`rel`، وخلو الصفحة من التدفق الأفقي عند العروض 390 و768 و1024 و1366 و1440 بكسل.

**حالة التنفيذ:** **Passed** — نجحت الاختبارات الأربعة في `e2e/path/t16-performance-redis-qa.spec.ts` في 2026-10-19 بعد تسجيل بيانات المواضيع. شملت القراءة والنسخ والمراجع وخلو الصفحات من التدفق الأفقي عند العروض المحددة. لم يُنفذ benchmark أو QA على تطبيق طالب؛ فحص صفحات الموقع لا يثبت ذلك.
