**التذكرة:** [مسار المشروع 15] ربط الواجهة بالخادم واختبار الرحلات
**المسار التسلسلي:** الموضوعان 45 و46 ضمن مسار بناء مشروع الطالب
**تاريخ المراجعة:** 2026-10-19
**نطاق المراجعة:** تدقيق تحريري للمصدر واختبارات القراءة والنسخ في المتصفح. اختبارات صفحات الموقع نجحت بعد تسجيل المواضيع؛ لم يتوفر Backend أو قاعدة اختبار لمشروع طالب في هذا العمل.

## 1. نتيجة المراجعة وحدود الدليل

راجعت المصدر التعليمي في `src/data/topics/wave3/t15-frontend-api-testing.ts` مقابل مخرجات الموضوعات السابقة ومواصفة المسار. صيغت المحطة في موضوعين منفصلين:

1. **الموضوع 45 — `frontend-backend-integration`:** يربط رحلة Frontend واحدة بعقد API وخادم مشروع الطالب الفعلي، ويشرح نقل الجلسة والصلاحيات وحالات الخطأ.
2. **الموضوع 46 — `full-stack-journey-testing`:** يشرح أنواع الاختبارات ورحلات النجاح والفشل ومستوى الدليل، ويطلب تسجيل النتائج المنفذة وغير المنفذة.

مخرج العقد من الموضوع 40 هو `docs/API_CONTRACTS.md`، ومصفوفة الأدوار هي `docs/PERMISSIONS_MATRIX.md`. أمثلة BorrowHub تستخدم المسارات وحالات HTTP الواردة في المادة السابقة، مع إبقائها دراسة حالة لا عقدًا عامًا لمشروع الطالب. لا تفترض المادة وجود Endpoint أو حقل أو غلاف خطأ موحد خارج وثيقة مشروع المتعلم.

هذه مراجعة تحريرية للمادة التي أُضيفت، واختبار Playwright يثبت قراءة دروس الموقع ونسخ أمثلتها فقط؛ لا يتصل بBackend طالب ولا يثبت تكامل المنتج.

## 2. مراجعة مخرجات الموضوعين

### الموضوع 45: ربط Frontend مع Backend (`frontend-backend-integration`)

- **الموقع في المسار:** `sequencePosition: 45`
- **المخرج المتوقع:** `docs/FRONTEND_API_INTEGRATION.md`، تغيير واجهة واحد مربوط بعقد API الحقيقي، ودليل طلب ورد من بيئة محلية أو اختبارية بعد تنقيح أي بيانات حساسة.
- **المتطلبات السابقة:** Frontend وخطة البيانات من المواضيع 34–37، عقد API ومصفوفة الصلاحيات من الموضوع 40، وإطار خادم واحد مع المصادقة والصلاحيات ومنطق العمل من المواضيع 41–44.
- **ما راجعته تحريريًا:**
  - وجّه الشرح الطالب إلى مخرجي `docs/API_CONTRACTS.md` و`docs/PERMISSIONS_MATRIX.md` ومطابقة العقد مع تنفيذ الخادم. وذكر أن Swagger/OpenAPI مرجع مفيد لكنه لا يثبت وحده أن التنفيذ الجاري يطابقه.
  - فرّق بين Cookie session وBearer token، وجعل نقل الاعتماد وإدارته تابعين لعقد المشروع. أشار إلى خصائص Cookie مثل `HttpOnly` و`SameSite` و`Secure` وإعداد CORS وCSRF المناسب بدل القول إن `credentials: 'include'` يكفي وحده.
  - جعل التحقق من الدور والملكية مسؤولية الخادم؛ إخفاء زر في Frontend تحسين للتجربة فقط.
  - شرح الدلالات الشائعة لـ401 و403 وأخطاء 404/409/422 وأخطاء الشبكة، مع التنبيه إلى احترام عقد المشروع وإلى إمكانية استخدام 404 لحجب وجود مورد.
  - وصف مقتطف `fetch` بأنه نمط توضيحي، لا endpoint أو schema جاهزًا. يحتوي السجل على زر نسخ للمقتطف.
  - قصر مثال BorrowHub على مساري `POST /api/v1/loans` و`POST /api/v1/equipment` الواردين في المادة السابقة، ونبّه إلى عدم نسخهما لمشروع مختلف.
- **التقييم التحريري:** **Passed** — المخرج والخطوات تتبع اعتماديات المسار، ولا تَعِد بتنفيذ Backend للموقع التعليمي أو بوجود اتصال اختُبر فعليًا.
- **دليل المنتج الفعلي:** **Not Run** — لا توجد رحلة مشروع طالب أو خدمة API لتأكيد الاستجابات أو الجلسات أو الصلاحيات.

### الموضوع 46: Testing ورحلات المشروع (`full-stack-journey-testing`)

- **الموقع في المسار:** `sequencePosition: 46`
- **المخرج المتوقع:** `docs/INTEGRATION_TEST_PLAN.md`، اختبارات مناسبة لطبقات Frontend وBackend وFull-Stack، و`docs/TEST_RESULTS.md` بنتائج مفصّلة.
- **المتطلبات السابقة:** رحلة مرتبطة في الموضوع 45، متطلبات PRD/SRS ومصفوفة الصلاحيات، وبيئة اختبار معزولة.
- **ما راجعته تحريريًا:**
  - فصل Unit/Component وFrontend مع Mock وAPI/Backend وFull-Stack browser journey، وحدد ما يثبته كل مستوى وما لا يثبته.
  - أوضح أن `page.route` أو route interception يجعل اختبار المتصفح اختبار Frontend مع رد بديل، حتى لو نقر الاختبار عناصر الصفحة؛ الاسم E2E وحده لا يرفعه إلى دليل Full-Stack.
  - أضاف رحلة نجاح BorrowHub لطلب إعارة عبر المسار الوارد في المادة السابقة (`201 Created`)، ورحلة فشل نفاد كمية (`409 Conflict`) تقتضي فحص الاستجابة والعقد وعدم إنشاء سجل أو إفساد المخزون. لم يخترع أسماء حقول أو شكل غلاف خطأ.
  - اشترط Backend وقاعدة اختبار حقيقيين للادعاء بFull-Stack، وعدم اعتراض الطلب المستهدف، مع فحص واجهة المستخدم والأثر الخلفي.
  - استخدم حالات Passed وFailed وNot Run حسب التنفيذ والدليل، ووجّه لتسجيل البيئة وcommit وأمر التشغيل دون أسرار.
  - أضاف زر نسخ لمثال Playwright يعلن صراحة أنه مثال Frontend مع Mock.
- **التقييم التحريري:** **Passed** — مستويات الدليل ومحدودياته واضحة، ولا يساوي نجاح Frontend نجاح المنتج كاملًا.
- **دليل الرحلات الفعلي:** **Not Run** — سيناريوهات BorrowHub تعليمات للاختبار المستقبلي، ولم تُشغّل على التطبيق أو الخادم أو قاعدة بيانات.

### ما يغطيه ملف Playwright

يغطي `e2e/path/t15-frontend-api-testing.spec.ts` صفحات قراءة الدرسين بعد تسجيلهما مركزيًا، واتجاه RTL، ونص العقد والجلسة والأخطاء، وروابط التنقل بين 45 و46، وأزرار نسخ المقتطفات والحافظة، وعدم التدفق الأفقي عند العروض الخمسة. هذه تغطية لمتصفح **الموقع التعليمي** فقط، وليست اختبارات للمشروع الذي سيبنيه الطالب.

سُجلت `t15Entries` في `src/lib/topicRegistry.ts` واختُبر فتح المسارين بعد التسجيل. نجحت اختبارات صفحات الموقع في 2026-10-19؛ لا يُعامل ذلك كدليل على تشغيل Backend أو رحلة مشروع طالب.

## 4. خلاصة تعليمية

المخرج التحريري واضح ومترابط: يبني الطالب ربطًا مطابقًا لعقد مشروعه في الموضوع 45، ثم يتحقق في الموضوع 46 من النجاح والفشل عبر مستوى اختبار محدد ويكتب حدود الدليل. نجح فحص المتصفح والنسخ والتنقل والتجاوب للموقع التعليمي. أهم شرط متابعة هو ألا يعلن Full-Stack Passed من اختبار Frontend أو Mock. تظل رحلة API الفعلية ومخرجات مشروع الطالب **Not Run** حتى تنفيذها وتوثيق شواهدها.
