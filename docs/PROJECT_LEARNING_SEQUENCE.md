# تسلسل مواضيع بناء مشروع الطالب

التاريخ: 2026-10-18.

هذا ترتيب تفصيلي مقترح استجابةً لقرار المستخدم: كل تقنية أو مفهوم أو مخرج موضوع مستقل، والمواضيع متسلسلة لبناء مشروع واحد. لا يعتمد عدد المواضيع أو ترتيبها على تقسيم الدورة السابق. روجعت القائمة مع المستخدم، وعُدّل موضع أدوات التنفيذ لتأتي عند بدء كود الفرونت بعد التحليل والتصميم؛ لا تعني هذه المراجعة حسم بدائل الخادم والاستضافة.

## طريقة استخدام المسار

- يبدأ الطالب بفكرة مشروع ويحتفظ بالمشروع نفسه عبر الخطوات.
- تأتي أدوات التنفيذ عند بدء كود الفرونت بعد اعتماد المتطلبات والمخططات والتصميم: AI Coding Agent وGoogle AI Studio وSkills وMCP، ثم ربط Stitch وتوثيق التصميم وأدوات تخطيط التنفيذ. لا تشترط خطوات التحليل المبكرة تثبيت بيئة البرمجة أو مهاراتها؛ يمكن إجراء مقابلة Grill Me في محادثة وحفظ المخرجات يدويًا.
- لكل موضوع: متطلبات سابقة، شرح، خطوات تنفيذ، برومبتات مناسبة، مخرج، وقائمة تحقق قبل الانتقال.
- يراجع الطالب المخرج قبل استخدامه في الموضوع اللاحق. هذا ترتيب تعليمي، ولا يفترض قفل الصفحات أو حسابات دخول أو تسليمًا آليًا.
- Git وGitHub والمراجعة والاختبار ممارسات مستمرة بعد تعلّمها؛ ليست إجراءات تؤجل إلى نهاية المسار.
- الاختبار يبدأ مع أول تنفيذ ويستمر معه؛ موضوع Testing يجمع الاختبارات والتحقق من الرحلات الكاملة.
- BorrowHub مثال مرافق داخل المواضيع، وتبقى قواعده خاصة به. لا ينتظر الطالب الموضوع الأخير ليرى التطبيق.
- Django وFastAPI بديلان لتنفيذ الخادم، وVercel وNetlify بديلان لنشر الواجهة. كل أداة موضوع مستقل، ويكمل الطالب المسار بعد البديل الذي اختاره. لم يُعتمد بديل افتراضي بعد.
- المواضيع المشروطة، مثل Redis واستضافة Linux، تظهر في موضع استخدامها مع توضيح متى يحتاجها المشروع ومتى يتجاوزها الطالب.
- لا يُطلب إنشاء كل ملف لمجرد اسمه؛ تكون الملفات المذكورة مخرجات عملية تخص مشروع الطالب، لا روابط تنزيل وهمية.
- فصل التقنية إلى موضوع مستقل لا يعني تدريس جميع ميزاتها أو بناء مشاريع منفصلة لتعلّمها.

## ضوابط الاعتماديات

- اكتشاف المتطلبات يسبق PRD وSRS؛ المخططات تعكس المتطلبات ولا تخترع قواعد عمل.
- تعلّم Mermaid يسبق مخططاته، وتعلّم PlantUML يسبق Use Case.
- Domain Model يسبق ERD، وERD وSequence يسبقان Class Diagram.
- Screen Inventory يسبق Stitch، والشاشة المرجعية تسبق تعميم Design System، واعتماد التصميم يسبق DESIGN.md.
- إعداد وكيل البرمجة ومهارات التنفيذ وربط MCP يأتي بعد Prototype عند بدء الفرونت؛ لا تُقدّم إعداداته العملية في مقدمة المسار. تظل أدوات الرسم في موضع المخططات، وGit وGitHub مبكرًا لحفظ وثائق المشروع.
- DESIGN.md يسبق التخطيط النهائي للواجهة والتنفيذ، مع تقديم TypeScript وReact قبل Next.js.
- عقود Frontend أولية حتى مراجعتها ضمن Backend API Spec؛ تعالج الاختلافات في الوثائق والطرفين قبل الربط.
- لا يبدأ تنفيذ الخادم قبل توفر متطلبات المشروع ومخطط البيانات وعقد API. يطبق الطالب إطار خادم واحدًا.
- فحص Frontend وحده لا يكفي لإعلان نجاح المنتج Full-Stack؛ فحص التكامل والمنتج الكامل يأتي بعد الربط وقبل النشر، ويتبعه فحص على البيئة المنشورة.
- هذه مواضيع متتابعة وليست توزيعًا زمنيًا معتمدًا للـ40 ساعة، ولا قائمة أوامر تثبيت تم التحقق من إصداراتها.

## المراجع المرافقة

مكتبة البرومبتات، والقوالب، والقاموس، والأسئلة الشائعة، ودراسة BorrowHub متاحة طوال المسار وتُربط بالموضوع المناسب. محررات ووكلاء البرمجة البديلة وأدوات الصور والمراجع البصرية تُشرح في صفحات مستقلة بحسب الحاجة، دون إلزام الطالب بتبديل بيئته أو بناء المنتج مجددًا بكل أداة.
